Research methodology guide

End-to-end BRD/SRS generation and evaluation

The application converts one text-extractable requirements PDF into traceable requirements, scenarios, and manual test cases. This guide follows the data through all three generation strategies and explains which experimental conditions remain fixed.

Controlled conditions

Source PDF, evidence chunking, schemas, core grounding rules, deterministic validation, quality calculations, and Judge policy.

Independent variables

Run type plus configured generation providers, models, prompts, thinking levels, output limits, and run token ceiling.

Generated artifacts

Requirements (REQ-*), scenarios (SCN-*), test cases (TC-*), citations, and explicit trace links.

Evaluation outputs

Validation report, requirement traceability matrix, deterministic quality ratios, and fixed-Judge precision, recall, and F1.

Shared system

System workflow overview

Every run shares intake, evidence preparation, deterministic quality gates, the independent Judge, and persistence. Only the generation strategy changes.

The strategies are alternatives, not a ranking. Compare saved runs using the same PDF and state every generation setting that differs.

Run type 1

Single Prompt

One model call receives the complete evidence, core grounding rules, and run-specific prompt. It must return one ArtifactBundle containing requirements, scenarios, test cases, trace links, and grounded citations.

Controls and handoffs

  • Configurable provider, model, prompt, and run token ceiling.
  • Gemini 3 models expose a configurable thinking level.
  • No intermediate generation batch is saved before the complete bundle.
  • Transient provider errors retry up to two times; invalid complete responses receive up to two schema-repair prompts.

Research trade-off: this is the cleanest baseline for orchestration overhead, but extraction, scenario design, case design, linking, and citation grounding compete inside one response.

Run type 2

Staged Single Agent

One shared provider and model perform three sequential tasks. Each typed result is validated by its schema and becomes explicit input to the next task.

Research trade-off: staged outputs expose where omissions arise, but an incomplete requirement catalog constrains every downstream scenario and test case.

Run type 3

Centralized Multi-Agent

A policy orchestrator partitions work, enforces worker ID ranges, and merges results. Analyst, Test Generator, and Reviewer are the configurable generation agents. The fixed Judge remains independent and is not part of that agent configuration.

Wave 1: requirement extraction

  1. Remote execution balances chunks across three worker groups; local execution creates bounded scopes and runs them sequentially.
  2. Analyst workers extract grounded candidate requirements using reserved ID ranges.
  3. Python logic merges duplicate candidates, combines citations and dependencies, selects at most 20 canonical requirements, and renumbers them.

Wave 2: scenario and test generation

  1. The orchestrator redistributes canonical requirements with relevant evidence and read-only dependency context.
  2. Test Generator workers create scenarios and test cases using reserved local ranges.
  3. Python namespaces and checks worker IDs, merges batches, removes scenarios without usable test cases, and normalizes derived links and citations.

Conditional Reviewer

The Reviewer is not an always-on fourth worker. It runs only when deterministic validation needs a targeted requirement-link repair or an allowed whole-bundle revision.

Research trade-off: specialization and smaller contexts can improve focus, but partitioning, parallelism, deterministic reconciliation, and agent-model choices all become experimental factors.

Fixed-Judge semantic coverage

The independent Judge evaluates every generated artifact bundle, including a bundle that ultimately fails deterministic validation. It is fixed to Gemini 3.6 Flash, medium thinking, the same two prompts, and a separate 100,000-token evaluation ceiling.

  1. Extract every atomic testable behavior, business rule, constraint, or requirement from the complete source as CU-* coverage units.
  2. Map each test case only when its steps and expected results directly exercise a known coverage unit.
  3. Discard unknown IDs and calculate precision, recall, and F1 deterministically.
TP = test cases mapped to at least one valid coverage unit
FP = test cases with no valid unit, including omitted mappings
FN = coverage units not covered by any test case

precision = TP / (TP + FP)
recall    = covered coverage units / all coverage units
F1        = 2 × precision × recall / (precision + recall)

One test case can cover several units. It counts once toward precision, while every distinct covered unit contributes to recall. Judge failure leaves semantic coverage unavailable and never changes the generation outcome.

Experimental implementation

Result-affecting technology

PDF evidence

pypdf extraction, whitespace normalization, section detection, 6,000-character chunks, stable IDs, and SHA-256 hashes determine the model-visible source.

Typed contracts

Pydantic models define requirements, scenarios, test cases, reviews, repairs, coverage units, mappings, and the final artifact bundle.

Provider adapters

Gemini structured interactions plus Ollama, LM Studio, and llama.cpp-compatible endpoints translate the same typed requests into provider calls.

Python orchestration

Prompt assembly, retries, token ledgers, worker partitioning, bounded local execution, and conditional correction determine call shape and order.

Deterministic logic

Citation canonicalization, ID checks, link validation, normalization, RTM construction, and quality calculations constrain and measure outputs.

Independent evaluation

The fixed Gemini Judge supplies semantic units and mappings; Python calculates the final coverage score.

Research record

PostgreSQL stores normalized results, metrics, events, and immutable configuration snapshots for later comparison.

Research boundaries

Interpretation and reproducibility limits

  • The metrics are not source-code coverage and do not prove that any test was executed.
  • They do not measure defect detection or prove that the source requirements are correct.
  • Semantic F1 is not compared with a human-authored gold set. The fixed Judge controls evaluator variation but does not remove model judgment.
  • Parallel scheduling may affect latency, while saved token and retry counters describe resource use rather than artifact quality.
  • Reproducible comparisons require the same source PDF plus the stored run configuration. State every generation setting that differs.
  • A missing F1 means evaluation was unavailable; it must not be interpreted as zero coverage.
